# PRD — TUNTON AI Flutter MVP

**Status:** Scope-locked for a one-day hackathon  
**Platform:** Flutter mobile application; Android is the required demo target  
**Deployment:** Runs entirely on the phone after installation  
**Minimum target:** Smartphone with 8 GB RAM; performance must be measured, not assumed  
**Pilot area:** Intramuros, Manila (one prepackaged, verified walking area)

## 1. Product statement

TUNTON identifies a **supported landmark depicted in a photograph** using on-device AI, places the confirmed landmark on a **bundled offline map**, and calculates a **walking route from a manually selected starting point** using an on-device pedestrian graph.

**Core promise:** Snap a known landmark, confirm it, and find a walking route without internet access or a cloud AI provider.

**Accuracy boundary:** Visual landmark recognition returns the location of the **landmark in the photo**, not necessarily the location where the photo was taken. The app must never claim to establish the user's exact position from visual matching.

## 2. Problem and intended user

A visitor in a low-connectivity area has a picture of a landmark but does not know its name or where it is on a map. Online photo recognition, place lookup, and navigation may be inaccessible. For the demo, a visitor within the supported Intramuros map can use a previously captured photo to recognize a supported landmark, choose a known starting point, and preview a walkable route.

## 3. P0 — Required capabilities (the complete MVP)

| ID | Required behavior | Acceptance condition |
|---|---|---|
| P0-01 | Pick a photo from gallery or take one with camera | User can submit a valid image on the demo Android device. |
| P0-02 | Run on-device vision embedding inference | Image is resized/preprocessed exactly as required by the bundled TFLite model; no external inference requests. |
| P0-03 | Compare with local reference-photo embeddings | Display at most three *distinct landmark* candidates in rank order. |
| P0-04 | Support uncertainty | Ambiguous/unsupported images can return **Not recognized**; don't force an incorrect match or label similarity as probability. |
| P0-05 | User confirms a candidate | No landmark is treated as selected until explicitly confirmed. |
| P0-06 | Show a true offline map | Intramuros map tiles, landmarks, labels, and route layers render in airplane mode from bundled assets. |
| P0-07 | Choose a manual starting point | User chooses a supported map landmark / mapped entry point as the route origin; no live GPS required. |
| P0-08 | Use the recognized landmark as the destination | Destination coordinates come from the verified offline landmark catalog, not generated by AI. |
| P0-09 | Compute local walking route | Shortest connected pedestrian route is calculated over bundled edges and drawn following their actual geometry. |
| P0-10 | Show distance and walking ETA | Total graph distance and an explicitly estimated walking time are displayed. |
| P0-11 | Work after disconnecting | The installed application cold-launches in airplane mode and repeats recognition, map rendering, and routing. |
| P0-12 | Handle unusable conditions | Missing model/data, invalid image, unsupported landmark, and disconnected route graph have clear non-fabricated error states. |

**Demonstration dataset:** Start with six distinct Intramuros landmarks and roughly three to five correctly labeled reference pictures per landmark. Use separate unseen photos for evaluation.

## 4. User journey (single approved journey)

1. Launch TUNTON with internet disabled.
2. Tap **Take Photo** or **Choose Photo**.
3. App computes a local embedding and compares it with the bundled landmark index.
4. App displays up to three candidate landmarks or **Not recognized**.
5. User confirms the intended landmark (the destination).
6. App pins that landmark on the offline map.
7. User manually selects a mapped starting point within the supported area.
8. App computes and displays the shortest available pedestrian route, total distance, and estimated walking duration.
9. If either point cannot connect to the pedestrian graph, app displays **Route unavailable** rather than a straight-line route.

The route is a **preview**, not live turn-by-turn tracking.

## 5. Hard out-of-scope boundary

Do **not** implement, scaffold, or create modules for:

- Cloud AI, hosted endpoints, remote databases, analytics, user accounts, authentication, or background sync.
- General/worldwide photo geolocation, citywide image recognition, or real-time Google Maps functionality.
- Live GPS navigation, automatic rerouting, voice guidance, live traffic, road closures, or routing outside the bundled map.
- OCR, EXIF-based geolocation, street-sign reading, geocoding, downloadable region packs, satellite imagery, or model training/fine-tuning.
- Autonomous agents, chatbots, AR overlays, user image uploads to a server, or large language models.
- Driving, cycling, accessibility-certified, or real-time safety-aware directions.
- iOS-specific polish or a separate desktop/server implementation during the Android-first hackathon.

Potential future features are **not requirements**; don't build abstractions "for later".

## 6. Functional rules

- Visual recognition is retrieval over a **finite, packaged landmark catalog**; unsupported areas must not yield invented coordinates.
- GPS metadata and phone position are not used to infer the route start in P0. Starting point is a deliberate manual choice.
- Show only one selected destination and one selected starting point per route.
- Use a fixed pilot-region bounding box; reject points outside it.
- An unknown/ambiguous match stays unknown unless the user deliberately confirms one of the displayed candidates.
- The map and route must not require online tiles, online fonts, geocoding, or remote service calls.
- A route follows verified walking graph edges; distance is the sum of edge lengths. ETA uses an explicitly documented fixed speed (default **4.5 km/h**).
- Show **© OpenStreetMap contributors** and comply with the source map/tile license.

## 7. Nonfunctional constraints

- **Hardware:** Target 8 GB RAM Android devices, CPU-only TFLite inference as the default and no concurrent large models. Measure peak usage on real hardware.
- **Offline:** No runtime internet access required; all needed tiles, graph data, reference index, images, and `.tflite` model ship with the app.
- **Privacy:** Photo data remains on-device; no upload or telemetry. Discard temporary images when not needed.
- **Reliability:** One inference at a time; initialization and missing-asset failures must show recoverable errors.
- **Speed:** Record image inference latency, route calculation latency, and memory use. Do not claim targets are met without measurements.
- **Licensing:** Use legitimately obtained images and geographic data. Do not bulk-download tiles from the public OpenStreetMap tile servers for offline packaging.

## 8. Acceptance test matrix

| Test | Expected result |
|---|---|
| Unseen photo of supported landmark | Actual landmark appears among candidates; user can confirm it. |
| Unseen image outside the known set | App can respond **Not recognized**, not fabricate a location. |
| Two look-alike landmarks | Display candidates and require confirmation. |
| Start and destination connected in graph | Route line follows mapped pedestrian edges; distance and ETA shown. |
| No pedestrian path found | **Route unavailable**; no misleading direct line. |
| Airplane mode, cold restart | Photo inference, offline map, and local route all still work. |
| Invalid image / missing required data | Clear error message; no crash. |
| 8 GB test device | Record actual memory and timings; report any limitation honestly. |

**Required proof for judges:** A release build installed on an Android phone; a disconnected start-to-finish demonstration; test photos not identical to reference photos; measured inference, routing, and memory results.

## 9. One-day execution priorities

| Window | Deliverable |
|---|---|
| Hour 0–1 | Flutter app launches; model and map assets acquired; six landmark records selected. |
| Hour 1–3 | Independent on-phone embedding match works; independent local graph route works; offline map renders. |
| Hour 3–5 | Connect photo → candidates → confirmation → destination → manual origin → route. |
| Hour 5–6 | Unknown/photo errors, no-path error, map/route clarity. |
| Hour 6–7 | Airplane-mode cold-launch tests; hold-out photos; memory/latency measurements. |
| Hour 7–8 | Fix blockers and rehearse the complete user journey. |

**Stop rule:** Once the P0 journey works, focus on reliability and testing. Do not expand the scope.

## 10. Canonical dependencies

- Flutter / Dart
- `tflite_flutter` with a bundled MobileNetV3 Small **image embedder** `.tflite` checkpoint
- `image_picker`, Dart `image` for picking/preprocessing
- `flutter_map`, `latlong2` for offline map display and route geometry
- `flutter_riverpod` only for the existing MVP state flow; do not add another state framework
- Pure Dart Dijkstra on a bundled pedestrian graph; JSON/asset-based landmark and embedding data
- Python + OSMnx may be used **only while preparing** the map and graph on the developer's computer; they are not phone dependencies.
